# Reference product port

## When to Use

Use for cross-framework product ports, source-backed parity planning, and bounded
implementation waves where behavior must match a reference application. For
source census/schema tooling alone, use wing-upstream-analysis instead.

## Procedure

1. Read owner decisions, repo instructions, roadmap and parity ledger. Inspect `git status --short --branch` and pin the reference revision. Keep reference repositories/tooling read-only unless separately authorized; preserve unrelated dirty changes.
2. Resolve parity before widening implementation: feature coverage, navigation, wording, layout, interaction/state/recovery behavior and host-local authority are distinct. For a requested 1:1 port, use the reference product as the target, not merely inspiration or equivalent outcomes. Record adaptations and unavailable features as differences. Route a request to match a named product's UI/UX as a reference-pinned redesign, not polish of the incumbent interface. When Impeccable governs the work, complete its init product record and new-work direction contract before UI edits; missing design artifacts do not justify downgrading the request. Match the reference's layout, density, typography, color roles and navigation treatment within the agreed slice, because preserving the old visual language can defeat fidelity even when controls still work.
3. Answer evidence questions by inspecting source/tests. Ask one native clarification question at a time only for consequential choices: platform priority, full local functionality versus remote subset, first milestone. Do not edit code/docs during a grilling interview; act after implementation authorization.
4. Lead with a complete daily-use workflow, not whichever isolated UI gap is easiest. For chat: connection, explicit profile/model, generation, approvals, authoritative stop, departure and exact-session recovery. Supporting shell polish serves this path. Preserve mobile usability while establishing the owner-selected desktop baseline; do not silently retain an obsolete mobile-first goal.
5. Trace every operation to its authority: direct runtime API, typed management adapter, local native operation or unsupported contract. Reference client calls do not establish advertised runtime support. A remote management service is an implementation choice, not an intrinsic prerequisite of every port. Full local functionality needs a bounded native-integration design; product approval does not authorize arbitrary host access, credential copying or runtime patches.
6. Before inspecting a serious successor candidate, capture a bounded snapshot of its requirement, implementation, nearest tests and intended outputs, including outputs that do not yet exist. Preserve that original snapshot through contract preparation; recheck it immediately before dispatch because another human or worker may deliver the repair meanwhile. On changed bytes or newly appearing outputs, reread and rerank instead of refreshing the old snapshot merely to pass admission. Compare the candidate with live cards and their exact file exclusions, not just titles: a disjoint objective can still overlap a blocked slice's reserved source. Before parallel dispatch, capture owned files' current contents and assign exact disjoint paths. Keep implementation and tests with one owner; separate docs, audit/design and later independent review. Include scope, deliverable, literal verification commands and stop conditions. For design delegation, also name the redesign/refinement mode, exact playbook and craft-floor references, pinned reference, artifact ownership, required viewport captures and bounded inspection rounds. Reserve the final brief comparison and detector decision for the parent; do not treat a builder's self-review as independent finish evidence. If the user corrects the mode while a worker is active, steer that worker before further edits, preserve existing changes, and provide the corrected contract rather than launching an overlapping replacement. Shared interfaces remain read-only or single-owned.
7. Pin existing behavior, observe a new regression failing for the missing behavior, implement minimally and rerun. Never weaken tests to obtain green output. Attribute changes against the lane baseline, not solely HEAD diff, which includes pre-existing work.
8. Inspect artifacts/raw logs rather than trusting summaries. Require each worker's final handoff to name changed files, resolved findings, exact commands/exits, log paths and remaining gaps; a final message reporting only a full-suite pass does not prove the assigned fix. Independently review and run fresh integrated checks after producer ownership releases. For Flutter use the repo's actual gates; common commands are `dart format --output=none --set-exit-if-changed lib test integration_test`, `flutter analyze`, and `flutter test --concurrency=1`. Record each exit separately and parse counts from the terminal summary, not progress lines. Run a full suite once per integrated code state unless the user explicitly requests a fresh run; otherwise repeat only after relevant changes, a demonstrated flaky result or incomplete execution, because duplicate green runs do not resolve native-build or authorization blockers. Execute every command in an explicitly requested gate, preserving its literal spelling and recording its own exit; a package-script test run alone does not satisfy separately requested formatting and analysis. For read-only verification, do not repair production/tests, apply formatting, change acceptance cards or broaden document ownership. Investigate failures through logs and source reads, citing assertion and implementation locations while separating demonstrated causes from hypotheses. Size the command timeout for the known suite duration and preserve complete logs. Save the requested receipt before reporting completion, including exact commands/exits, log paths, parsed pass/fail/skip counts and failure references; if output is too sparse to establish counts, report counts as unknown rather than reusing a previous run's totals.
9. Exercise the user surface when feasible. Before capturing an interaction state, reach it through the real input path, move the pointer outside keyboard-focused controls, wait longer than the control's explicit transition duration, and assert that focus remains on the intended control. Reduced-motion settings do not prove that individually authored button transitions have settled; premature captures can make a working focus border appear defective. When a reviewer requests recapture, replace only the invalid images, preserve unaffected captures, verify unchanged source hashes, update the affected screenshot hashes, and submit the complete packet for a fresh review. Recapture corrects evidence, not implementation, and carries no build approval. Separate unit/widget, fixture, compiled browser, native plugin/device and actual runtime/provider evidence. Default `flutter test` does not execute device integration journeys. Local stream teardown is not authoritative Stop; restoration must retain canonical identity and prove no duplicate submission. For native launchers and paginated restoration fixtures, follow [native workflow harnesses](references/native-workflow-harnesses.md) before treating a delivered harness as adequate coverage.
10. Update roadmap/receipts with results and gaps. Link independent source-review receipts from the affected parity checkpoint and task handoff, and name exactly which gate they close; source-consistent proposals do not authorize implementation or qualify runtime behavior. For repeated documentation passes, compare scoped fingerprints, current task status and the linked evidence before editing; preserve a no-op when the supported claims remain accurate. Report changes, checks, counts and log directory concisely. Green tests/source review do not establish runtime/card/release acceptance. For scheduled continuation follow [recurring continuation](references/recurring-continuation.md).

## Review pitfalls

- Test intentional modal barriers separately when a semantics container shields navigation from nested-route blocking; the boundary may also retain navigation exposure behind a nested modal.
- Test selected destination, keyboard focus, child/draft identity and short-window scaling separately; desktop resize coverage does not establish draft retention across replacement by a mobile shell.
- Distinguish source-matching behavior from deferrals; an in-memory preference is not relaunch persistence.
- Verify Flutter IconButton focus through rendered output, not ButtonStyle properties alone. An opaque focused Ink overlay can mask a correctly resolved shape border even after transitions settle. Test expanded/collapsed controls in both themes. A toggle-only transparent focused overlay can preserve a continuous outline without changing unfocused hover behavior.
- Inspect font-face unicode ranges before naming reference typography. Hermes Desktop's Latin UI uses Manrope; Cairo declarations cover Arabic glyph subsets. Do not describe a system-font fallback as exact reference typography.
