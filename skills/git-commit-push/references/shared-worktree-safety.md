# Committing a shared worktree

When several agents work one checkout, "commit everything" is a concurrency problem before it is a git problem. The dirty set is not yours alone, and a file can be mid-write while you stage it. This is the order that ships the tree without pushing a half-finished edit to a shared branch.

**Authorization sets scope; authorship establishes provenance.** An explicit repo-wide
ship request covers all eligible changes in requested scope, including completed
cross-agent work. Take delivery ownership after provenance, scope, completion, secrets
and candidate-bound verification checks; attribute contributors and receipts in commit
messages. Authorship alone never excludes changes or yields NO-OP. Narrow path/topic
requests and autonomous worker/card runs remain scoped; local-only requests never
authorize push, and audit never authorizes Git writes. Exclude live writer/lease hunks,
unfinished or unverifiable work, secrets and unapproved product scope; never blind-stage.

## When to use

Load when asked to commit or push a large or accumulated dirty tree, when `git status` shows paths you did not create, before any `git add -A`, or when a repo's own plan calls for committing per component.

## Procedure

1. **Size and group the tree before staging.** `git status --porcelain | awk '{print $2}'`, grouped by top-level component; `git diff --stat -- <group> | tail -1` per group. Never stage blind — the count also tells you whether the tree is still growing.
2. **Find who is still writing.** List the profile's running work cards (e.g. `hermes kanban list --profile <name>`, filtered for `running`), then order dirty paths by age:
   ```bash
   now=$(date +%s)
   # per path: echo "$(( (now - $(stat -c %Y "$f")) / 60 )) min  $f"
   ```
   A path written seconds or a couple of minutes ago is being written now. Corroborate with the process table and the owning card's own output: `pgrep -af "<gate>|<test runner>"` plus the log path its verification writes to. A running card is not by itself proof the area is mid-verification — an in-flight gate is, and while one runs the file will change under you again.
3. **Exclude actively-written files instead of waiting on them.** They stay dirty for their own card's commit — nothing is lost. Name what you held back and why, in both the commit message and the report.
4. **Bound the risk with a check, not with nerve.** A compile or parse of the affected component (`go build ./...`, `tsc --noEmit`, `flutter analyze`) shows the tree is not syntactically broken; it does not show the work is complete. State which check you ran and what it does not prove. Then run the repo's own guards for the areas you staged — their verdict can flip merely because a file became tracked (see the tracked-file pitfall below). **Order it `git add` → run the gate → `git push`**, and let the gate exit 0 before pushing. A tracked-file-only guard cannot see an unstaged new file, so a green run taken *before* staging reports on the wrong tree; and a gate still running in the background while you push bounds nothing — that push ships the exact state the gate exists to catch, and the repair becomes a second commit on an already-published branch. A gate can also outlive the host's per-command timeout, and a run cut off by that cap is **not** a passed gate: when the gate may run longer than the cap, start it as a tracked background job and wait for its exit code before pushing; redirect the run to a log and append its status (`cmd > /tmp/gate.log 2>&1; echo "EXIT=$?" >> /tmp/gate.log`) so the verdict survives a truncated console tail. (That is about where the gate runs, not licence to push while it is still running.) If the gate's output reached you truncated, you no longer hold its exit code — recover the verdict from the chain instead: a `&&`-joined gate that reached and passed its final step exited 0 at every earlier step, and saying you inferred that is honest, whereas quoting a count you truncated away is not.
5. **Scan the staged set for secrets and confirm ignore coverage before staging.** Credential-shaped grep over exactly the `git status` paths; confirm `.gitignore` covers the risky roots (`data/`, `.env`, `.local/`, tool output dirs). A path that looks like a database or a local service root must be *shown* to be ignored, never assumed.
6. **Commit per component, not as one blob.** A hundred-path single commit is unreviewable and unrevertable, and mixed commits make bisect useless. One message per group describing that group's change. If the repo's plan or ledger states a commit shape, follow it.
7. **Push, then verify the remote is actually level.**
   ```bash
   git push && git fetch -q origin
   [ "$(git rev-parse HEAD)" = "$(git rev-parse origin/main)" ] && echo MATCH
   ```
   The `git push` success line is not proof; read both revisions back. Classify the direction before acting on a "pull" or "merge" instruction: fetch, then `git rev-list --left-right --count @{u}...HEAD`. `N  0` (behind N, ahead 0) is the ordinary case; `0  N` ahead-and-not-behind means the inbound merge has nothing to bring in — the pull is a no-op and the real gap is outbound, so report the pull as a no-op rather than implying a merge happened, and say which direction you completed instead. A tree dirty in the paths a merge would touch blocks that merge, so a verified-but-uncommitted file is a prerequisite of the instruction rather than scope creep. Read the commit message back *before* the push too: a stray token in a message that has left the host is permanent on a shared branch, since correcting it takes a force-push you must not do.
8. **Close the loop in the ledger.** If a tracker item authorised the commit, mark it resolved with the SHAs and note what was held back. A ledger still saying "uncommitted" after your push is a false statement you introduced. When your change joins an existing commit-authorisation entry, add your paths to that entry rather than creating a rival one — and keep the entry an explicit path allowlist. Reread the ledger immediately before writing and assert your anchor text still exists; abort the write if it does not, because a concurrent agent may have re-scoped that entry and your edit could widen an authorisation.

## Temporary-index landing without a development branch

Use this recipe only when repository policy permits canonical main commits and
explicit delivery authority exists. It isolates the committed payload, not writers;
keep one writer and refuse any observed input drift.

1. Pin `HEAD` and fresh remote main. Back up the real index and each touched file
   under ignored project evidence. Classify staged and unstaged changes separately;
   a temporary index alone does not preserve either after `HEAD` advances.
2. Set `GIT_INDEX_FILE` only for individual Git calls. Run `git read-tree <base>`,
   then apply the reviewed owned delta with `git apply --cached --3way`. Inspect
   conflicts and the candidate diff before resolving them. A failed application
   is not a candidate: rebuild the temporary index from the pinned base before
   trying the corrected patch. For an explicitly retired file whose historical
   contents differ, inspect and archive those bytes before removing only that
   authorized path with `git update-index --force-remove -- <path>`.
3. Record `git write-tree`; export the complete index with `git checkout-index
   --all --prefix=<snapshot>/`. Qualify that tree and compare all relevant exported
   blobs afterward. Keep candidate Git overrides out of build-tool environments.
4. Before committing, calculate two three-way reconciliations for every touched
   path: old base → local worktree → candidate, and old base → real staged blob →
   candidate. Resolve only evidenced in-scope conflicts; preserve unrelated local
   hunks. Record the complete planned outputs before writing any canonical file.
5. Recheck canonical `HEAD`, the real index bytes and every touched worktree input.
   Commit with the temporary index using ordinary `git commit`; require the new
   `HEAD^{tree}` to equal the qualified tree. Do not disable hooks or substitute a
   fabricated receipt if a hook changes the tree.
6. Install the precomputed worktree reconciliations and update only touched real-index
   entries, preserving unrelated staged entries. Retain backups until this readback
   proves the staged and unstaged residuals survived. Push normally and verify the
   exact remote main SHA; advancing main this way is direct delivery, not a PR merge.

## Pitfalls

- **A dirty path being written right now is not a path you can commit.** File age is the tell; the running card that owns the area is the corroboration.
- **A live card invalidates its component's gate, not only its files.** Component-scoped gates (`go build ./...`, `flutter analyze`, a package-wide test run, a language's full suite) read whatever is in the tree, including the concurrent card's half-written edits. So a green *or* red result there is not evidence about your commits, and the compile check of step 4 cannot show the tree is sound when the breakage is mid-write next door. Hold the whole component and say why, then ship the components you can still gate: holding every component because one is live, or reporting a poisoned gate as passed, are both wrong. Identify the live card first (`hermes kanban list --status running --assignee <profile>`) and let its newest paths tell you which component it owns.
- **A tracked-file-only guard passes locally and fails the instant you commit.** `git grep` — and every guard built on it — searches tracked files only, so a new file dropped into a directory an existing guard scans is invisible while untracked, and turns that guard red the moment your commit makes it tracked. Before staging, find the guards whose scan covers the new files' directories and run them against the tree you are about to create; a green run on the current (untracked) tree is no evidence about the post-commit tree. When the guard is right and the file genuinely must contain the banned literal — a guard's own hermetic self-test — the correct fix is a documented, path-scoped exception inside the guard, never a weakened or narrowed scan.
- **The tree can change between two reads of it.** A count that moved between measurements means a writer is live — re-measure immediately before staging rather than trusting an earlier tally. The same drift can land on files you already gated, because a concurrent pass may *refine your own uncommitted work* rather than clobber it: a diff that grew by a few lines while your gate ran is usually that, not corruption. Compare `git hash-object` per path against the blobs your gate covered and treat a mismatch as a re-gate, not a reason to abandon the work — read the changed hunks first to confirm they extend your change instead of contradicting it, then re-run the gate over the new bytes and commit the refined file as one unit, naming the other pass in the commit message. Holding back a *better* version of your own work is a stall, not caution.
- **`git add -A` on a shared tree stages other agents' work by definition.** Prefer explicit pathspecs plus exclusions for the files under active write, and verify the exclusions actually took (the residual dirty set should be exactly the files you meant to hold back).
- **One commit is not automatically the right answer to an emphatic "all".** Grouping is a deviation worth stating out loud, not a silent reinterpretation — say what you grouped and why.
- **Do not re-run a whole suite to justify a commit you were told to make.** Each change carries its own recorded verification; cite that, and report the suite as not run rather than implying you executed it.
- **Prove the artifact is unchanged instead of re-running its gate.** When a flag or reviewer calls a path unverified and the tree may have moved since your green run, compare blobs rather than repeat a slow gate: `git hash-object <path>` against `git rev-parse HEAD:<path>`. Equal blobs mean the exact file your gate exercised is what is on disk now, so the recorded result still stands; a differing blob needs re-gating. State which of the two you established — re-running green bytes implies the first run was inconclusive.
- **A hard path count in a ledger entry is stale within minutes on a shared tree.** Name the command (`git status --porcelain`) as authoritative and list the authorized eligible paths, with provenance; a fixed number guarantees a false statement by the next commit, and re-editing the number each time is churn that races other writers.
- **A shared ledger file carries other passes' uncommitted prose into your commit.** Trackers such as `TODO.md` and `BLOCKERS.md` are written by several passes, so a ledger path that is already dirty contributes their accumulated edits to your diff. Confirm the added lines are that kind of ledger text before committing, and say in the report that the commit contains them — never present the whole diff as your own change. Edit such a ledger with anchored find-and-replace per entry rather than one whole-file write: a full-content write races the other passes' prose and is refused outright when the copy you hold is stale, so the targeted edit is both the safer and the accepted shape.
- **An authorisation naming explicit paths is an allowlist, not shorthand for "everything dirty".** Adding your verified paths to it is correct; widening it to the whole worktree is not — it would publish whatever another agent happens to be mid-edit on.
- **Eligibility is per hunk, not per file.** A shared fixture can contain completed in-scope work beside a live migration. Inspect every hunk; include completed authorized hunks regardless of author. When live, out-of-scope or unverified hunks cannot be separated safely, hold the whole file and its dependent code/tests.
- **Read recorded provenance instead of requiring another author's permission by default.** A finished card's branch (`git diff --name-only $(git merge-base HEAD agent/<profile>/<card>)..agent/<profile>/<card>`) identifies its paths, not an exclusion list. With explicit repo-wide authorization, check completion and target bytes, then integrate eligible unshipped work; committed on an agent branch does not mean published to the requested target. Without that authorization, remain within the worker/card or path allowlist. Live ownership/leases remain excluded. Read the delivered path set back (`git diff --name-only <base>..HEAD`), confirm scope and attribute other contributors rather than calling their work your own.
- **Stale/forked ledgers are reconciled on fresh upstream, never restored over it.** Compare task identities and additions/removals, reconstruct genuine authorized unshipped edits in an isolated candidate using supported `goals.py task`/`add-task`/`fmt`/`render` operations and anchored prose edits, validate and inspect the resulting diff. Preserve newer remote entries; never delete remote lines merely to match a stale copy. Stale-only copies yield no new commit. NO-OP means no actual unshipped delta in requested scope regardless of author; held eligible work is HELD/ASKED, not NO-OP. Report behind/diverged status separately.
- **Never stage an implementation without the test that pins it.** When the test file is co-owned or mid-write, hold the code with it rather than committing the pair's two halves separately — an untested change on a shared branch is a worse commit than no commit, and holding the pair costs one pass. Splitting a change from its regression test is a defect you introduced, not tidiness.
- **A finished card's branch is redundant only when nothing it holds is *absent* from the target.** Test it with an add-only diff, then discount what the target deliberately dropped: `git diff --name-only --diff-filter=A HEAD agent/<profile>/<card>` lists what the branch has and HEAD lacks, but a file HEAD removed on purpose — dead code you deleted, a retired module — shows up there on every pre-deletion snapshot, so a naive reading flags a whole batch of redundant branches as unique content. Subtract those paths and re-check; only a path genuinely absent from the target blocks deletion. The inverse error is worse: reading "the branch differs from HEAD" as "already shipped" loses work, because a branch usually differs merely because the target moved past it. Report the check and its result, and delete with `-D` only once it comes back empty.
- **"Is my work already on the remote?" is not answered by `git diff --name-only HEAD..origin/main`.** That range lists every path differing in *either* direction, so it includes files only you added — which the remote does not have at all — and reads exactly like "the remote already has my work". Ask per file instead, by blob: `git rev-parse HEAD:<path>` against `git rev-parse origin/main:<path>`, where an **empty** origin side is the answer "absent there". Let `git rev-list --left-right --count @{u}...HEAD` settle the branch's direction and `git diff --stat origin/main HEAD` settle the content. Getting this backwards loses work: the wrong read declares "already shipped" about a commit nothing else contains, and the retraction costs more than the check.
- **A rejected push on a dirty shared tree integrates by merge, not by rebase.** Rebase borrows the working tree, so an unrelated dirty set blocks it — and stashing that set to clear the way is forbidden, since it is other agents' work. Merge refuses only where incoming paths actually collide with local modifications, so prove disjointness first: `comm -12 <(git diff --name-only HEAD origin/main | sort -u) <(git status --porcelain --untracked-files=all | awk '{print $2}' | sort -u)`. Empty means merge; anything listed means stop, because overlapping incoming work is an owner decision rather than a merge to improvise. A disjoint merge keeps your commit, leaves the alien dirty paths untouched, and makes your branch a descendant of the remote — so the push becomes a true fast-forward that rewrites nothing published. Re-run the gate afterwards because the *tree* gained upstream work, and confirm your own paths' blobs are identical before and after: that is what proves the merge moved nothing of yours.
- **A card dispatched from a premise you have since corrected keeps writing that premise into the tree.** Correcting a finding does not reach the worker that was handed it, so the card carries on editing production files on the retracted reading — and those edits land in the same shared tree you are gating and committing from. Record the retraction on the card itself, then stop it (`hermes kanban comment <id> "<what changed and why>"`, then `hermes kanban block <id> "<reason>"`), and check whether it already touched files before staging anything: those bytes stay dirty for its owner, untouched by you. Leaving it running is not neutral — it is unreviewed work built on a premise the record now contradicts, in the tree your gate reads.
- **A ledger task is `in_progress` only once a card actually owns it.** A dispatch helper that answers with an existing card id (an `already_owned`-style outcome, returned with the card's own persisted budget) means the slice already has an owner: reconcile that card instead of forcing a second worker for the same work. Tick the ledger at that handoff, not in anticipation of it — a task marked in-progress with no card behind it is a false record you will have to retract, and the picker selects from the same ledger you write.
- **A shared checkout that is behind upstream can hold *older revisions* of files upstream has since changed; committing the tree publishes a regression, not a delivery.** Several agents push from sibling checkouts, so one of your files may be an unmerged card branch's revision sitting over a newer upstream one — the worktree blob equals that branch tip's blob, and both predate `origin/<branch>`. Prove each path is current before treating a dirty shared tree as the delivery queue: `git hash-object <path>` against `git rev-parse origin/<branch>:<path>` — equal is current, a *differing* upstream side is a newer upstream revision the worktree copy would revert. Name the newer revision in the report and ask; never flush a tree whose bytes an upstream commit already replaced.
- **Classify the dirty set by where its bytes already exist before you call it a delivery queue.** On a shared checkout a dirty path is often the content of an unmerged `agent/*` branch parked in the tree, not new work. Resolve every non-deletion path's blob against every ref in a single pass (`git cat-file --batch-check=%(objectname)` fed `<ref>:<path>` lines for all refs) and bucket them: matches one unmerged branch (redundant with that branch), already on the remote (no delta), genuinely uncommitted (the real queue). A tree that is mostly branch content is a scratch integration area — land the branches, not the tree.
- **Botched-command artifacts land in an untracked tree and get staged by accident.** A zero-byte file whose name carries shell metacharacters (`server-vigia/3}`) or a nested duplicate of the component's own subtree (`server-vigia/server-vigia/src/...`, produced by running a command from inside the component dir) is junk from a failed redirect or a mis-based `cp`. Scan `git status --porcelain --untracked-files=all` for both shapes, exclude them, and leave them for their author to remove rather than deleting another writer's path.
- **Rehearse a divergent landing in a scratch worktree before asking.** It costs seconds and turns a vague question into a specific one: `git worktree add --detach <scratch> origin/main`, then per branch `git merge --no-edit <branch>` and `git merge --abort` on conflict, recording the conflicted paths; `git worktree remove --force <scratch>` after. The rehearsal reports which branches merge clean, which conflict and where, and whether a supposedly finished branch is only a ledger/autogoal base (it touches `goals.json` alone) — all without touching `main` or the shared index.

## Boundaries

- **Committed is not deployed.** A push is not a release, an image rebuild, a restart of a live system, or a schema migration — each needs its own authorisation, even when the commit itself was ordered.
- **Some paths are never yours to commit** under any instruction: secrets, local database or service roots, machine state, and anything an instruction file marks protected. Do not file **project ledgers** under "generated artifacts", though — `goals.json`, `TODO.md`, `BLOCKERS.md`, and a design system's `PRODUCT.md`/`DESIGN.md` are tracked project files, and a ledger that is written by automation but committed by nobody is not durable. Treat the delivery policy as the authority on which is which, and verify rather than assume: `git ls-files <path>` answers whether the file is versioned at all, and a rendered view inside a tracked file does not regenerate the machine-readable source behind it. Refusing a tracked ledger because it *looks* generated silently drops the backlog other automation reads.
- **Preserve other agents' work in the tree.** Excluding a live file is correct; reverting, stashing, or cleaning the worktree to make the commit tidy is not.
- **Approved work that has no branch is unprotected work.** A finished reviewed card with only dirty-tree bytes needs a durable commit. With explicit repo-wide ship authorization, include eligible completed work in the requested target after the delivery checks. For an autonomous card without that authorization, use its own `agent/<profile>/<card>` branch and temporary-index helper, preserving HEAD, the real index and dirty files. Record the branch/sha and provenance; neither mode implies deployment.
