# Codebase audit verification

## When to Use

Load before writing up any audit, issue report, coverage gap, or "this looks wrong" finding about a repository — especially when the evidence came from a text search (`search_files`), a heuristic scan, an import graph, or a config file's own self-description.

## The core rule

A static heuristic produces a **hypothesis**, not a finding. Before a claim enters a report, open the consumer or companion file and confirm the mechanism. In a single audit pass, several plausible-looking findings died this way; each cost one read to kill and would have cost the report's credibility to keep.

- Separate **verified** findings from **hypotheses** in the write-up, and state what you did *not* verify (builds not run, toolchains not installed, hosts not reachable).
- An aggregate verify script you cannot run is not a reason to verify nothing: run its constituent steps individually and report the aggregate itself as unrun.
- Never upgrade "I reasoned about it" into "I checked it".
- **A check that printed nothing did not pass.** A verifier invoked with a flag its runner does not accept is a silent no-op: a flag belonging to a different package manager, or a subcommand that does not exist, makes the command emit an empty line, and `tail -1` around it renders that blank exactly like a verdict. Read the exit status and require non-empty output before recording a pass, then re-run the command correctly — reporting the blank as green is the same error as reporting a gate you never started.
- **An edit that returned an error or a timeout is not an edit that cleanly failed.** A killed execution cell can lose its state partway, after some writes have already landed, so inspect the target's actual content before deciding whether to retry. Assuming success leaves the tree unverified; assuming failure and re-applying blind can double an edit.
- **Some files are consent-gated, and a refusal is not a workaround prompt.** A write to an agent-instruction file (`AGENTS.md`, `CLAUDE.md`) is refused unless the user approves it at that moment — a timed-out approval prompt is *not* consent, and the refusal explicitly forbids retrying or reaching the same edit another way (a different tool, a shell redirect). A documentation-maintenance mandate does not authorise instruction-file edits. Deliver the finding as a blocked item carrying the exact current text, the proposed replacement, and the evidence, so the owner can approve the wording itself. The same boundary limits **scope** and not only file type: a mandate to maintain documentation does not authorise adding a validation framework, a CI check, or a test, however well the gap is evidenced — propose those as tasks with a concrete acceptance check instead of quietly implementing them under the docs mandate.
- **Grep the codebase for the symptom's own vocabulary before writing a behavioural finding.** The string a symptom surfaces under — a log line, an event name, a database column — is usually written beside the code that emits it, so searching that vocabulary finds the comment or test that says whether the case is intended. Treat a comment naming the exact observed divergence as a strong counter-hypothesis: it usually means the behaviour is designed (a prune, a fallback, a deliberate skip) and the "defect" is the reader's inference from aggregate counts. One grep is cheap; a retracted headline costs the report's credibility and queues a task nobody should work.
- **A field that maps several code paths to one value is not evidence of which path ran.** When a decision is recorded through one shared value, an occurrence of that value reads as intent even for the paths that reached it by fallback. Find the function that writes the field and count its write sites before arguing a decision from it; if the distinction matters, the fix is to have each path write a distinguishable value.
- A guard that passes while its own source is uncommitted is not evidence about the committed tree — check `git status` before treating a PASS as authoritative. The same applies to a guard's **scan target**: a check built on `git grep`, or any tracked-file-only scan, cannot see an untracked file, so a new file dropped into a directory that guard scans passes now and turns it red the moment a commit makes the file tracked.
- **A validator's rejection is a hypothesis about your input, not a fact about it.** When a checker reports a field missing or empty that you can plainly see is present and populated, read how the checker tokenises before rewriting the content. A fixed-field contract parser usually keys on the label immediately followed by its delimiter, so a qualifier wedged between the two (`Field (note):`) makes the field read as absent while the text sits right there — and two rounds of re-authoring the value in different words fail identically. Read the parser once, then fix the shape: the label must be the bare token, with any qualifier moved into the value.

## False-positive classes that recur

- **Tests live where you did not look.** One subtree's convention is not the repo's convention: a project can place tests both co-located *and* under `__tests__/` directories, while a stale instruction file claims only the first form. Search the whole test tree for the module's **basename** before declaring a module untested.
- **Audit the runner's coverage, not only its green result.** Compare every first-party test suite with the CI commands and local runner. Run standalone suites separately when they mutate import paths; explicitly exclude model-backed, networked, or live-profile tests from offline discovery. Test discovery with fixtures so adding helper tests does not silently leave them outside CI. Validate structured frontmatter with the real YAML parser: matching `name:` and `description:` lines cannot establish their types, reject duplicate keys, or prove that a skill has a body. Require a nonempty input set so a broken discovery pattern cannot pass vacuously.
- **"Imports nothing and is imported by nothing" is rarely dead code.** Go `main` packages, Python `__init__.py`, standalone CLI scripts, `testdata/` fixtures and generated validators all look orphaned to an import-graph heuristic.
- **A name-reference scan cannot establish deadness across a shared file scope.** Constructs that put several files in one scope — Dart `part`/`part of`, C# `partial`, extension methods, same-package top-level members — make a symbol reachable by a sibling file with no import and no name-level mention anywhere else. A class-name grep therefore reports such a file as dead while the compiler still needs it, so never write "no references" from a scan: compile the component (`flutter analyze`, `tsc --noEmit`, `go build ./...`), which is what actually names the couplings. Expect them in **both** directions — members of the file you are removing that survivors still call (relocate those), and declarations in the survivors that only the doomed file used, which the delete turns into freshly-unreferenced code (remove those in the same pass, or the change ships new warnings).
- **A suspicious constant may be converted at the call site.** A value whose name and units disagree with its use is often correct — the consumer may convert units and correct for geometry first. Read the usage before reporting a unit bug.
- **Import edges may be resolved at package, not file, granularity.** An import of a package can resolve to *every* file in its directory, inflating per-file fan-in. Reason about coupling at the granularity the resolver actually used, and say which granularity you mean.
- **Artifact directories inside the tree pollute repo-wide scans.** A generated graph, an `intermediate/` dir, a tool output tree, or an agent transcript directory (`.pi-subagents/`) makes text search (`search_files`) and line-count heuristics unreliable — one JSONL transcript can dwarf the source that mentions the same symbols and outrank it in a hit count, so a "23 hits" reading is really "3 hits plus a log". Exclude them explicitly rather than sifting the output. Version-control internals belong on that exclusion list too: `grep -rl <value>` also matches `.git/shallow`, `.git/packed-refs`, `.git/ORIG_HEAD` and `.git/logs/HEAD`, so a "N files carry this revision" count is inflated by files no reviewer means — 22 raw hits collapsed to 10 real tracked files once `.git/` and the agent-artifact dirs were filtered. Report the exclusion set alongside the count. One shell trap in the same breath: `grep -rn -- '<pattern>' --include=X dir` silently turns `--include` into a path operand, because `--` ends option parsing — the count comes back empty or searches the wrong set. Put the flags before the `--`, or drop the `--` entirely.
- **Doc/code drift cuts both ways.** An instruction file that describes the layout wrongly will mislead your scan *and* is itself a legitimate (minor) finding — report it as documentation drift, not as the larger bug it looked like.
- **A bare filename in prose is not a root-relative link.** Resolving every backticked token as a repo-root path invents dozens of "missing reference" findings that actually resolve inside their component (`startup.ts` → `server-vigia/src/lib/server/startup.ts`). Resolve bare names by searching the tree for the basename; only a path-qualified reference can be checked root-relative. A missing-path count is a finding only after that search, so report the check method with the result.
- **Tokens that merely contain a slash are not paths.** The same family invents findings from an MCC/MNC pair (`334/003`), a numeric ratio, a git branch name (`agent/<profile>/<task>`), and an HTTP route literal (`/api/v1/auth`) — each reads as a path to a naive pattern and none of them is one. Exclude those shapes before counting, or the count is noise that buries the real hits.
- **A "not found" is a hypothesis about your scan, not about the tree.** The mirror error of the bullet above is a false negative: reporting a symbol or key as absent when the grep never looked at the file type that defines it (a shell script's constant while scanning only `.ts`/`.py`), or when it searched a path you guessed rather than resolved. Confirm the probe's own assumptions — the file exists, its extensions are in scope — before a miss becomes a finding, and re-run it correctly rather than reporting the doc as wrong.
- **A path a document names as removed is intended absence, not broken-link drift.** Read the sentence before flagging the reference: "the former `tools/setup.sh` helper no longer exists" is correct prose about a deleted file. Classify it as a deliberate historical reference and route it to the project's drift-ignore mechanism; reporting it as drift is a finding the owner has to dismiss, and it recurs on every pass until suppressed.

## Config constants are not knobs until something imports them

A file declaring "every tunable in the system lives here" can be partly aspirational. Reference-count its exports: if a constant appears only at its own declaration, nothing reads it, and the real value is hardcoded at the use site — so tuning it is a no-op and any advice to tune it is wrong. The same check finds genuinely dead config left by a refactor.

Report these as **placebo knobs**. This is worth checking wherever a project claims a config file is the single source of truth for behaviour.

The same defect sits one level out, in the deployment configuration surface, where it cuts **both ways**: a key documented but read by nothing (an inert knob — an operator sets it and nothing happens, which is worse than a missing feature because it looks like it worked) and a key read by code but documented nowhere (undocumented behaviour). Enumerate the reads from source (`(?:process\.env|env)\.([A-Z][A-Z0-9_]+)` over the non-test sources) and diff against the documented keys in the config template, reporting each direction separately. Two traps, both hit in one pass: a key read through an indirection (a helper that takes the name as an argument, `process.env[name]`, a destructure) is invisible to a literal-accessor scan and reads as "documented but unread" — false negative, so confirm by reading the consumer; and a key consumed only by compose/Dockerfile interpolation (`${KEY:-default}`) or a shell script falls outside a source-only scan entirely.

**Pick the fix direction from the code's own convention, not from which side is easier to edit.** When the documented name is inert because the code reads only an older spelling, rewriting the template to the legacy name is the wrong repair. Check the sibling keys first: if they follow `NEW ?? LEGACY` — the newer name is the declared deployment contract and the older is a fallback kept for existing operators — then the *code* is the stale half. Honour the documented name with the legacy as fallback, and mirror the surrounding comment that states the convention. Editing the template instead contradicts the file's declared contract and changes which key an operator must set.

**A required key's failure mode is part of its documentation.** Before writing "set `KEY`", trace what happens when it is absent: a step that exits non-zero under a `set -e` parent aborts the whole pipeline, while a step gated on a runtime probe (`if command -v <dep>; then …; else warn; fi`) prints a warning and continues, leaving the effect silently undone. One script can carry both branches, so a missing key may hard-fail, soft-skip, or do one of each depending on the runtime — enumerate each path and document the consequence an operator will actually hit, not merely the key's name. A step whose whole purpose is a side effect (a backfill, a rewrite, a reindex) is the one to trace: when it soft-skips, the recorded state still claims the work is done.

**A sync guard must derive its expected set from source.** A guard that diffs a *hand-typed* list of keys against the template can only confirm that names someone once wrote down are still present. It cannot see a name the code reads but nobody documented, nor a documented name that nothing reads — which is how an inert knob survives a green suite indefinitely. Enumerate the reads from source, and state the scan's boundary in the guard's own comment so a blind spot is not mistaken for coverage.

**Zero references is necessary evidence, not sufficient.** The scan above misses the worse half of the defect: a constant imported at *one* site while the same value stays hardcoded as a literal in sibling consumers. Those two sites drift apart silently and no reference-count can see it. After the zero-reference pass, grep each constant's **value** as a literal across the sibling consumers and list the duplicates.

### Fixing placebo knobs

- **Fix duplication, not singleton literals — decide the scope before editing anything.** A literal that appears once, in one consumer, is local detail: centralising it buys indirection and no correctness, and it buys churn in load-bearing code. Only a value appearing at **two or more** sites *that share a semantic* is a divergence risk worth wiring. Ask "same threshold, or merely the same number?" — sites can share a value with different boundaries (`<= 1.5` vs `< 1.5`) or unrelated meanings. Wire the shared constant, preserve each site's own comparison operator, and surface the boundary disagreement to the owner as a question rather than silently picking a winner. Say which single-site literals you deliberately left alone and why, or the next reviewer reads them as misses. A literal that already carries a module-local name (`const RSRP_MIN_GDOP = 0.1`) is in the same category — leave it, and note only that its value may still collide with a differently-named central constant.
- **Put a shared constant where the dependency arrow already points.** Before choosing a home for a centralised value, measure the import direction between its consumers: `grep -rl "from '<layer>" <other-layer>` returning nothing means one layer is deliberately pure while the other imports it freely. The constant belongs in the **pure** layer, imported by the other. The reverse placement forces a backwards dependency, so the "centralisation" lands as a layering violation and review rejects it. A home the codebase's own arrow forbids is not a home — and a second config file is itself a cost, since the guard can no longer assume one source to parse.
- **A SQL pre-filter that mirrors a TS helper is the same fact in two places.** Detectors often re-implement a helper's predicate in SQL to narrow rows before the helper runs in code. Read the helper body: if it combines named constants (`sightings >= X && distance <= Y`), the SQL block repeating those comparisons **is** the mirror, and wiring both to the same constants is provably right rather than a guess. Quote the helper body as the evidence for the pairing.
- **Pair a constant to its site by reading the consumer, never by matching the value.** Values collide heavily — a dozen tunables can share `20`, half a dozen share `3` — so value equality cannot tell which constant belongs at which site. Importing the wrong one is a silent behaviour change in load-bearing code, and review will not catch it because the diff looks mechanical. Read each consumer to identify its own site, and retract any earlier "values agree, therefore behaviour-preserving" claim you based on value matching.
- **Substituting a constant for a literal is not always text-neutral.** In SQL, `literal` → `$1` changes the query, not just its spelling. Before editing, look for tests that assert query shape and check how the driver types bare parameters; prefer the interpolation form the file already uses for its other constants. Say explicitly that mocked tests do not exercise the driver's parameter typing. In a file that passes positional `$1..$n` parameters with a values array, interpolating a constant as a *new* bound parameter renumbers every index after it — inline it as plain template text instead, which leaves the SQL byte-identical and is the safer half of this whole class of edit.
- **Add a guard and prove it discriminates.** Parse the export list and fail when an exported tunable has no consumer outside its own file. Then run the guard against the *pre-fix* revision of its input and confirm it flags exactly what you fixed. A guard that has never been seen to fail is not a guard. Record the guard's blind spot in its own comment so the next reader does not over-trust it. Ready-to-copy vitest guard: `templates/export-consumer-guard.test.ts`.
- **Measure a heuristic guard's false-positive rate before shipping it, and reject the predicate if it cannot reach ~zero.** A value-matching rule over *all* constants once produced ~960 candidates, almost every one noise (unit conversions, `LIMIT`, percentile fractions, rounding idioms). A guard needing hundreds of exemptions is worse than no guard — it trains reviewers to ignore it and it blocks unrelated work. Narrow the predicate until it measures clean (restricting "the literal equals a threshold" to *comparison* contexts removed the entire noise class), then ship that.
- **Choose the guard's scan scope by measurement, not by taste.** Run the candidate predicate over several scopes and count hits: the detector subtree may score 0 while the whole source tree scores dozens of unrelated collisions. Ship the scope that measures clean and record the number, so the boundary reads as measured rather than arbitrary.
- **Make the guard fail loudly when it finds nothing to check.** A guard that derives its inputs by parsing can silently go blind after a refactor and then pass vacuously forever. Assert a floor on the parsed input count, so breakage of the parse is a failure rather than a green tick.
- **A collision guard reports candidates, not a resolution.** When a scan keys on a value, several constants legitimately share it (a `0.5` boundary matched two). Emit the location, the literal, and every candidate constant — never assert which one the author meant. The developer resolves it; the guard only has to make the collision visible.
- **Falsify the guard by reintroducing the defect, then restore byte-identically.** Running it against the pre-fix revision proves it *would have* caught the class; re-breaking one live site proves it *does* fire now, on the exact predicate you shipped, with the error message a real developer will read. Restore and confirm the file is byte-identical before moving on. Cross-language collision guard ready to adapt: `templates/threshold-collision-guard.test.ts`.
- **A falsification harness must prove its mutation landed before it trusts the red result.** Assert the edited file's hash actually changed. A harness whose edit silently no-ops, or empties the file, reports a successful falsification that proves nothing — and an emptied guard exits 0, so the red you expected never arrives and the green reads as a pass. One trap produces precisely that: `open(p, 'w').write(open(p).read().replace(...))` truncates the file at open time and then reads back nothing, so every guarded file becomes empty and every check passes; read the content into a variable first, then open for write. A `sed -i` whose pattern matches nothing fails the same silent way. Edit a copy you can restore, compare the hash before and after, and treat "the file did not change" as a harness error rather than a result.
- **Scale the verification to the blast radius, not to the diff.** A wiring change confined to one subtree can be gated by that subtree's own tests. The moment the edit reaches a *shared or pure* module whose consumers sit elsewhere, run the **whole** unit suite — the local subset cannot see the other consumers, so a green subtree run is a false comfort. State which scope you ran and why it was the right one.
- **Widening a module's surface breaks the tests that partially mock it — and that failure is a harness bug, not a behaviour bug.** A mock factory listing exports by hand (`vi.mock('m', () => ({ fn }))`) returns `undefined` for every export added later, so the consumer silently compares against `undefined` and takes one branch: dozens of failures appear in files you never touched, which reads as "my change broke behaviour". Spread the real module inside the factory (`async (importOriginal) => ({ ...(await importOriginal()), fn: vi.fn() })`) so the mock cannot drift again, and remember the same class in Python — when the helper under test *also* calls the function you stubbed, a blanket fake hands its own canned output back as the value under test; dispatch inside the fake on the arguments and assert which call it was.

## A live state snapshot is a sample, not a state

A status endpoint, a persisted `state.json`, or a `docker logs` tail shows the system at the instant you read it. Two inferences from that material are cheap to get wrong, and both produce a confident, wrong finding:

- **Sample past the designed cap before calling a rotator or scheduler stuck.** A component built with a maximum consecutive-run cap looks pinned when you read only as many cycles as the cap allows: two consecutive same-target entries are exactly what a `maxConsecutive = 2` design *should* emit. Read more consecutive cycles than the cap, or read the allocator's own decision record, before writing "it never rotates". Put the sample size in the finding so the reader can judge it.
- **Find the cursor by name, not by resemblance.** A persisted state blob carries several similarly-named counters (a plan index, a rotation index, a roster cursor). Reading the wrong one manufactures a stuck-at-zero story. An `omitempty` field that is *absent* is also indistinguishable from a genuine zero — absence is not evidence the cursor is stuck, only that it was not serialised. Read the writer to learn which field is the real cursor and what its absent value means.

When the claim does not survive that check, withdraw it against the ledger explicitly rather than restating it in softer words.

## Plan and status documents are hypotheses too

A roadmap, backlog, or status summary is a claim about the tree, not evidence about it. Two failure modes recur, and both are cheap to check:

- **Receipts are verifiable.** A "shipped `<commit>`" line can be checked without reading the diff: `git cat-file -e <sha>^{commit}`, confirm `git merge-base --is-ancestor <sha> HEAD`, and check the commit subject actually describes the claimed feature. Where the plan names its tests, locate them and run them. Do this *before* repeating the claim in a report — and before you write a commit id into anything, confirm the same id appears in the document you are quoting, so you cannot introduce an invented receipt.
- **The ledger may already name the artifact you just created.** After a tool mints a task/card/ticket id, grep the project's own ledger (root `TODO.md`, a status page, a board export) for that id *before* reporting it as new work. An existing record naming it means the item was already completed and your creation was a duplicate: reconcile it and say plainly that you duplicated it, rather than presenting a redundant dispatch as progress. The same search steers selection — an item recorded as done is not a candidate, however stale the symptom looks.
- **Named paths may not exist in this checkout.** A backlog item can cite candidate files belonging to a different project, and its own text may admit it — "historical source: …; unavailable in this checkout". Resolve every named candidate path *before* selecting the item as work. A plan whose candidate paths are all absent is not a task list for this tree, and re-selecting it burns a whole pass; record the conclusion so the next pass does not re-derive it.
- **An entry's own evidence pointer rots while the entry stays true.** A record can cite a section heading or a task id that has since moved — the id living in a different tracker than the entry claims, the section retitled, the cited file relocated — so a reader who follows it lands on nothing. When re-verifying a still-active entry, resolve the pointer to a live location (open the cited path and confirm the named heading, symbol or record is still there) and correct the citation **in place**, leaving the entry's status unchanged: a dangling citation is a documentation defect, never evidence the underlying condition is resolved, and never a reason to open a second entry for the same condition. Say which entries you actually re-checked, and leave a `Last checked`-style stamp alone on any entry you could not verify from the tree — an entry scoped to an intent, a pending authorisation or a future session is not repo-verifiable, and stamping it asserts a re-evaluation you did not perform.
- **A record's claim about its own authority is checkable against the user's own instructions.** An entry asserting that an action is "outside the agent's standing authorization", or that it "requires owner approval", is making a factual claim about the user's directives, not about the tree. Before repeating or acting on that claim, search the recorded directives for one that grants exactly that action: when one exists, the record is wrong on that point, and the real gate is usually the *side effect* that needs operator timing — a restart that ends a measurement window, a migration that locks a table, a rebuild that invalidates a running run. Correct the stated reason in place and keep the gate; a wrong reason is not evidence the underlying condition resolved, so do not close the entry on it.
- **Audit a structured record against its declared schema mechanically, then re-run the check after editing.** A long-lived ledger accumulates entries that each look complete while a required field is missing on nearly all of them, so read the schema the record declares (or the policy governing it) and compare every entry's field set against it rather than eyeballing a sample. Report extra and missing fields per entry, and check ids for duplication. Re-run after the edit: the record you just repaired is the one most likely to be wrong.
- **When a checker flags a rule you just changed, suspect the checker first.** A validator carries its own copy of the expectations — an allowed-field list, a required set, a section split — so the run immediately after you extend a rule can flag the very thing you added, and can apply one section's rules to another. Re-read its expectations against the declared schema, fix the checker, and only then treat a failure as a fact about the artifact.
- **The record can be right where your own earlier claim was wrong.** When a ledger's figure disagrees with one you reported from the same artifact, re-measure rather than assuming the ledger drifted: a count taken from a summary (classes carrying an annotation) can be wrong while the ledger's stricter count (annotations actually present) is right. Correct whichever the measurement contradicts — including your own earlier claim — and say that you did.
- **A contract or integration document's surface list is a hypothesis about the tree.** Enumerate a component's actual calls from its own source — the API path literals it emits — before trusting a cross-project guide's route list, which drifts and can attribute to a component a route it never calls. Where a machine-checked guard pins the surface (endpoint → route file → method → payload key), that guard is the source of truth: derive the documentation from its declared contract and cite it, rather than hand-maintaining a parallel list no check can falsify. Put each side of the surface on the page that owns it and cross-link, instead of adding a third copy. Verify a rendered doc change in the built output — the anchor ids readers link to exist only after the site build — not only in the source.

**Keep a register of surfaces you have already cleared.** A pass that finds nothing still cost a full pass, and the next one will re-run the same searches unless the result is written down. Record the surface, the check used, and the finding (or the clean result), with the explicit caveat that the entry expires the moment that surface changes — dependencies, dates, environment facts and shipped code are not permanently true, so the register narrows re-checking rather than replacing it. Say plainly which entries are conclusions about *this checkout* rather than durable rules.

**A prior finding is a hypothesis about the current tree, like any other.** Before re-reporting, re-fixing, or queueing an earlier audit's item, confirm it is still open. A ledger or tracker that records its closure — naming the change that closed it — means acting on it again is duplicated work and repeating it misstates the tree; an audit whose three findings are all closed should report zero, not three. Do not trust the closure note either: verify its own claim against the files it names. The same discipline applies to a surface *someone else* has claimed since — resolve which files a concurrent worker has touched, including its documentation, before editing anything in that area, and stay out of it rather than racing a live writer.

**When two places state the same fact and disagree, verify before editing either.** The more detailed document is the likely source of truth — but only after checking its claims against the tree, because "reconcile the summary to the plan" propagates the error when the *plan* is the stale copy. Quote the receipt evidence in whatever you change, so the reconciled line stays checkable.

A status summary collapsing several shipped items into one "next" is the common shape: the index line is short and rarely re-read, the plan is long and updated per session, so they drift silently. Neither is guarded, because both are prose.

**A dated document gets a dated correction, not a rewrite.** When a page carries its own date (a status page, an experiment log, a research record), read that date before treating its claims as current — a months-old "known limitations" list describes the tree as of then and will read as authoritative anyway. Check both halves of a limitation independently: the claim itself *and* the mechanism it names (a run model, a service, a file path) can each have gone stale on its own. Example shape: "there is no automated integration test, and e2e needs the running systemd service" — the tests had since been written and the service retired, so the entry was wrong twice over. Correct it by appending a dated note stating what no longer describes the tip and **preserve the original prose**, exactly as a retracted claim is withdrawn; never edit the historical text in place.

## For rules about what a build or tool includes, let the tool decide

When the question is "does X actually get included / excluded / uploaded", do not reason about pattern semantics — build the smallest input that makes the real tool answer. A one-second probe against the real config beats a 45-minute build, and beats an argument.

**Never hand-type an identifier into a probe.** Stub paths, symbol names and filenames copied by hand pick up typos that make the pattern correctly fail to match — which then reads as a finding and wastes a report cycle. Generate probe inputs from real filesystem entries (`search_files(target='files')`, a shell glob, `git ls-files`), never by retyping them.

## A test that fails on a missing ancestor is a harness gap

The first test to exercise a UI side-effect path — a snack bar, a dialog, a route push — usually fails on an assertion thrown from inside the widget, not in the code under test. A messenger that exists with **no descendant** to present to asserts in debug (`ScaffoldMessenger.showSnackBar` → `_scaffolds.isNotEmpty`), and a harness that pumps the page straight into an app root supplies exactly that: the messenger, and nothing behind it. So read the failure as a statement about the tree you built. Find the ancestor the widget assumes — the page may build no `Scaffold` of its own and rely on a shell above it — and give the harness one, rather than weakening the assertion or dropping the test.

Add that wrapper as an **opt-in** parameter on the shared pump helper. A helper used by dozens of existing tests must not silently gain a new ancestor for all of them, and the default has to leave every existing case byte-identical.

Then check the finder, not only the tap: assert the side effect **scoped to the surface it creates** (`find.descendant(of: find.byType(SnackBar), matching: find.text(...))`). The page usually renders the same value in its own panel, so an unscoped `findsOneWidget` fails on two matches while its unscoped inverse (`findsNothing`) passes for the wrong reason — the page showing the text regardless of the button. Scope both directions to the widget the action produced.

Docker build contexts and `.dockerignore` rules: load the `docker-build-context-verification` skill.
